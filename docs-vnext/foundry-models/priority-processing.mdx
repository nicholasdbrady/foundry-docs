---
title: "Enable priority processing for Foundry Models"
description: "Enable low-latency priority processing, override service tiers per request, and monitor usage and costs."
---

Priority processing provides low-latency model inference with pay-as-you-go billing. Enable it on a deployment, override the tier for individual requests, and monitor which tier served each request.

## Prerequisites

- An Azure subscription
- A `GlobalStandard` or US `DataZoneStandard` model deployment
- Model version `2025-12-01` or later

## Latency targets

Targets are measured as p50 request latency over five-minute periods.

| Model version | Target |
| --- | --- |
| `gpt-6-sol`, 2026-09-22 | 99% above 80 tokens per second |
| `gpt-5.6-terra`, 2026-07-09 | 99% above 70 tokens per second |
| `gpt-5.6-sol`, 2026-07-09 | 99% above 66.5 tokens per second |
| `gpt-5.5`, 2026-04-24 | 99% above 50 tokens per second |
| `gpt-5.4-mini`, 2026-03-17 | 99% above 100 tokens per second |
| `gpt-5.4`, 2026-03-05 | 99% above 50 tokens per second |
| `gpt-5.2`, 2025-12-11 | 99% above 50 tokens per second |
| `gpt-5.1`, 2025-11-13 | 99% above 50 tokens per second |
| `gpt-4.1`, 2025-04-14 | 99% above 80 tokens per second |

For `gpt-5.4` and `gpt-4.1`, requests estimated to exceed 128,000 prompt tokens are processed and billed at the standard tier.

## Availability

Global standard deployments support priority processing in these regions:

`australiaeast`, `brazilsouth`, `canadacentral`, `canadaeast`, `centralus`, `eastus`, `eastus2`, `francecentral`, `germanywestcentral`, `italynorth`, `japaneast`, `koreacentral`, `northcentralus`, `norwayeast`, `polandcentral`, `southafricanorth`, `southcentralus`, `southeastasia`, `southindia`, `spaincentral`, `swedencentral`, `switzerlandnorth`, `switzerlandwest`, `uaenorth`, `uksouth`, `westeurope`, `westus`, and `westus3`.

US Data Zone standard deployments support priority processing in `centralus`, `eastus`, `eastus2`, `northcentralus`, `southcentralus`, `westus`, and `westus3`.

Model availability differs by deployment type. Check the portal when creating a deployment or see the [current availability matrix](https://learn.microsoft.com/azure/foundry/openai/concepts/priority-processing#priority-processing-availability-by-deployment-type).

## Enable priority processing on a deployment

In the Foundry portal:

1. Create or edit a supported model deployment.
1. Turn on **Priority processing**.
1. Save the deployment.

To configure a deployment through the REST API, set:

```json
{
  "properties": {
    "service_tier": "priority"
  }
}
```

Use `default` for standard processing.

<Note>
Priority processing uses the same quota allocation as standard processing.
</Note>

## Override the tier per request

The Responses and Chat Completions APIs accept `service_tier`. Set it to `priority` to request priority processing:

```bash
curl -X POST "https://YOUR_RESOURCE.openai.azure.com/openai/v1/responses" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "model": "YOUR_DEPLOYMENT",
    "input": "Summarize the latest support case.",
    "service_tier": "priority"
  }'
```

| Deployment setting | Request setting | Processing tier |
| --- | --- | --- |
| `default` | `auto` or `default` | Standard |
| `default` | `priority` | Priority |
| `priority` | `auto` or `priority` | Priority |
| `priority` | `default` | Standard |

If `service_tier` is omitted, it defaults to `auto` and uses the deployment setting.

<Info>
Starting September 25, 2026, unsupported `flex` requests return HTTP 400 instead of falling back to standard processing. Verify model support or use `service_tier: default`.
</Info>

## Monitor usage

In Azure Monitor:

1. Open the Azure OpenAI resource.
1. Select **Metrics**.
1. Add **Azure OpenAI requests**.
1. Filter by deployment.
1. Split the metric by **ServiceTierRequest** and **ServiceTierResponse**.

The response `service_tier` also indicates whether priority or standard processing served the request.

## Monitor costs

In Azure Cost Management, filter cost analysis by the `deployment` billing tag and select the deployment name. Requests processed by the standard tier are billed at standard rates, even when the original request asked for priority processing.

## Limitations

- Regional standard and EU Data Zone standard deployments aren't supported.
- Rapid traffic increases, peak demand, or long-context requests for designated models can move a request to standard processing.
- A ramp increase of more than 50% tokens per minute in less than 15 minutes can trigger standard-tier processing.

<Tip>
If workloads repeatedly exceed the ramp limit, use Provisioned Throughput Units for steady-state capacity or combine PTU with priority processing for bursts.
</Tip>

## Troubleshooting

| Symptom | Resolution |
| --- | --- |
| Requests move to standard processing | Increase traffic gradually, check for peak capacity, and verify long-context restrictions. |
| Latency target isn't met | Confirm the response was served by the priority tier and that the model/version is supported. |
| Cost is lower than expected | The request might have been served and billed at the standard tier. Check `ServiceTierResponse`. |
